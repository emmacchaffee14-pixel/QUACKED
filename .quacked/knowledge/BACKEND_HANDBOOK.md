# Quacked Backend Handbook

**Last verified against live code + live database: 2026-07-29.**

This is the canonical, ground-truth reference for Quacked's Supabase backend —
every Edge Function, the real database schema (pulled live via
`information_schema`/`pg_policies`, not guessed from code), and the
cross-cutting business rules that span multiple functions.

**Partial auto-sync**: sections wrapped in `<!-- AUTO:...:START/END -->`
markers (the DB schema tables and the tier-gating table) are mechanically
regenerated from the live database and source code — run
`node cursor/scripts/update-handbook.mjs` (or the `/update-handbook` skill)
after touching a migration or a tier-limit constant. **Everything outside
those markers is hand-written prose and is NOT touched by the script** —
function descriptions, ⚠️ notes, and "Known discrepancies" still need a human
(or a Claude session re-run) to update after a real behavior change. If
you're reading this and something looks wrong, trust the code and the live
DB over this document, then fix this document.

Supersedes `archive/docs/Quacked_Backend_Handbook_v3.6.docx` (explicitly
marked superseded in its own header) as the backend-authoritative source.
`cursor/AGENTS.md` is frontend-scoped and defers to this file for backend
internals.

## README — how to keep this file current

This file is **partially self-updating**. Two categories of content:

1. **Mechanical facts** (DB schema tables, tier-gating table) — wrapped in
   `<!-- AUTO:...:START/END -->` markers, regenerated by a script from the
   live database and source code. Safe to re-run anytime; never edit inside
   these blocks by hand, it'll just get overwritten next run.
2. **Hand-written prose** (function descriptions, ⚠️ notes, "Known
   discrepancies") — everything outside the markers. The script never
   touches this. Update it yourself, or ask a Claude session to re-derive it
   (the same investigation process used to build this file originally).

### To regenerate the mechanical sections, run one of:

```bash
# from cursor/
npm run update-handbook

# or directly
node scripts/update-handbook.mjs
```

Or in Claude Code, just ask it to update the handbook — a `/update-handbook`
skill is set up at `cursor/.claude/skills/update-handbook/SKILL.md` that runs
the same script.

**Requires**: the `supabase` CLI linked to this project (`supabase link`),
same auth this repo already uses elsewhere. No other setup.

**What it does**: pulls live columns/CHECK-constraints/RLS-policies per table
via `information_schema`/`pg_policies`/`pg_class`, and parses the actual tier
limit numbers straight out of `check-gate`/`arithmetic-attempt` source. Fully
mechanical — no LLM call, so it's fast (usually) and always factually
accurate to whatever the DB/code say *right now*.

**When to run it**: after any migration, or after changing a tier-limit
constant in `check-gate` or `arithmetic-attempt`. It's also safe (a no-op
that reports "nothing changed") to just run periodically if you're not sure.

**Heads up**: each run makes ~28 sequential calls to Supabase's Management
API (columns + constraints + policies × 7 tables). This has been
inconsistently slow in practice — under 2 seconds some runs, over 2 minutes
others — seemingly on the API/CLI side, not the script's logic. If a run
hangs, that's most likely why; it will still finish and report correctly.

**After running it**: check the script's output. If it lists changed
sections, go skim the hand-written prose nearby (especially "Known
discrepancies") — a mechanical change (a column added/removed, a limit
number changed) often means a prose note referencing the old fact is now
stale too. The script will tell you *what* changed, not whether your prose
still describes it correctly.

## Security model — read this first

- Every Edge Function builds its Supabase client with the **service-role
  key** (`_shared/service-key.ts`), which bypasses Row Level Security
  entirely.
- Every function has `verify_jwt = false` set in `supabase/config.toml`.
  **Auth is not independently verified against a JWT** — each function trusts
  whatever `user_id` is passed in the request body. Anyone with the
  publishable key (client-safe, intentionally public) can call any function
  with an arbitrary `user_id` and it will act on that user's data as if they
  were authenticated.
- This is mitigated in practice by RLS on the tables themselves (a
  well-behaved client can only ever read/write its own rows directly), but
  the *functions* do not enforce that boundary — they are effectively "trust
  the caller" admin endpoints reachable by anyone who has the publishable key
  (which is everyone, by design, since it's meant to be public).
- **Do not treat this as acceptable long-term** — flagging it here so it's
  visible, not because it's fine. If you're doing a security pass, this is
  the first thing to fix (e.g. requiring a verified JWT and deriving
  `user_id` from it server-side instead of trusting the body).

not urgent).

`subscription_tier`, `is_admin`, `streak_days`, `last_active_date`,

not exist on the live table.** The migration file was never actually run
against production. If you're relying on `username` anywhere in the
frontend, it will fail. Either run this migration for real, or remove the
stale migration file if `username` was abandoned.

## Edge Functions

All 9 live at `cursor/supabase/functions/<name>/index.ts`. All build a
service-role client via `_shared/service-key.ts` (see below). All accept
`OPTIONS` for CORS preflight and return `corsHeaders` on every response.

### `check-gate`
**Purpose**: gate for case-drill volume, and a read-only "peek" for
arithmetic limits (arithmetic *enforcement* lives in `arithmetic-attempt` —
see "Tier gating" below, this was a real double-counting bug fixed
2026-07-28).

**⚠️ Sprint 02 (2026-07-29)**: the case-drill path's **difficulty gate was
removed entirely.** Previously free tier was locked to `duckling` only; now
every tier can request any difficulty (`duckling`/`billable_bird`/
`fully_quacked`) — difficulty is a free user choice, not a tier-gated
feature. `case_difficulty` is still accepted in the body but is no longer
read for gating purposes (kept for backward compatibility, harmless to send
or omit). The `tier_locked`/`DIFFICULTY_DISPLAY` response path no longer
exists — don't expect it. Only the daily **volume** check (`CASE_TIER_RULES[tier].limit`)
still gates case drills, unchanged.

**Body**: `{ user_id, request_type?: "case_drill"|"arithmetic", case_difficulty?, admin_password? }` (omit `request_type` or set anything other than `"arithmetic"` for the case_drill path — this includes all four `generate-case` modes waddle/swim/dive/fly, which all count against the same `daily_drill_count`, not the arithmetic counter).

**Reads**: `user_profiles(is_admin, subscription_tier, daily_drill_count, last_drill_date, daily_arithmetic_count, last_arithmetic_date)`.

**Writes** (case_drill path only — arithmetic path never writes):
`user_profiles.daily_drill_count`/`last_drill_date` — resets to 0 at day
rollover, increments by 1 on every allowed call.

**Gating**: `ADMIN_OVERRIDE_PASSWORD` env secret bypasses everything if
matched in `admin_password`; `profile.is_admin` always bypasses. See
"Tier gating" table below for the actual volume limits (difficulty is no
longer part of this table's gating story, only volume is).

**Response**: `{ allowed, reason, tier?, tier_display?, message?, upgrade_prompt?, drills_remaining?/reps_remaining? }`.

### `get-skills`
**Purpose**: tier-gated skill dashboard.

**Body**: `{ user_id, admin_password? }`.

**Reads**: `user_profiles(subscription_tier, is_admin, streak_days)`,
`user_attempts` (total/correct counts, all tiers); pond+ also
`user_attempts(case_id, correct, response_time, created_at)` (last 20);
big_duck/admin also `user_skills`, `skill_history` (last 100).

**Gating**:
- `free` → `{ locked: true }`, no stats at all.
- `pond` → accuracy/streak/last-20-attempts, `skill_breakdown_locked: true`, no `skills`/`categorized`.
- `big_duck`/admin → full breakdown: `categorized` (`needs_work` <50, `developing` 50–74, `strong` ≥75), `most_improved`/`most_struggled` from summed `skill_history.delta`.

### `update-skills`
**Purpose**: adjust skill scores after a drill attempt (called by the
frontend after recording the attempt in `user_attempts`).

**Body**: `{ user_id, case_id, correct, skipped?, hint_used? }`.

**Reads**: `generated_cases.skills_tested` for the case.

**Writes**: upserts `user_skills` (clamped 0–100) per skill tested, inserts
one `skill_history` row per skill, updates `user_profiles.streak_days`/`last_active_date`.

**Scoring**: skipped → delta 0; correct+hint → +4; correct no hint → +8; wrong → −12.

**Response**: `{ updated_scores, delta, streak_days }`.

### `arithmetic-attempt`
**Purpose**: **sole gate + increment owner** for the arithmetic daily
counter (dual-mode).

**Body**: `{ user_id, check_only?: boolean, operation?, difficulty?, problem?, correct_answer?, user_answer?, correct?, response_time?, rigor?, timed_out? }`.

**Mode 1** (`check_only: true`): read-only peek, no writes. Returns
`{ allowed, tier, remaining, message?, upgrade_prompt }`.

**Mode 2** (default): inserts into `arithmetic_attempts`, enforces
`ARITHMETIC_LIMITS`, force-resets `rigor` to `"practice"` server-side for
non-paid/non-admin users regardless of what the client sent (anti-tamper —
timed modes are paid-only), updates `user_profiles.daily_arithmetic_count`/`last_arithmetic_date`/`streak_days`/`last_active_date` (arithmetic feeds the daily streak too, same as drills).

**Response**: `{ recorded, correct, stored_rigor, streak_days, remaining }`.

### `generate-case`
**Purpose**: the core content-generation function — most complex of the 9.

**Body**: `{ firm?, difficulty, template_id?, skill_target?, industry?, archetype?, tone?, mbb_firm?, mode? }`.

**⚠️ Sprint 02 (2026-07-29) + follow-up (same day)**: added `mode: "waddle"|"swim"|"dive"|"fly"`,
**mode affects presentation only** — `calculate-case` is called identically
regardless of mode (`{ template_id, difficulty }`, no `mode` passed through),
so `worked_solution`/`final_answer` are guaranteed identical across all four.
Any caller that omits `mode` gets exactly today's (pre-Sprint-02) behavior —
`mode` defaults to `"fly"`. Zero Anthropic calls for waddle/swim (verified via
latency: ~1-2s vs. ~8s+ for dive/fly) — a real cost/latency reduction, not
just unused response fields.
- `swim`: no AI call. `question` is one of the archetype's `question_patterns`
  picked at random and used **verbatim** — none of the current
  `question_patterns` contain interpolation placeholders (they're already
  complete questions), so there's nothing to "fill in" on the question
  itself. `facts` is a deterministic bullet list built from every variable
  `calculate-case` actually randomized for this instance (`humanizeVarKey`/
  `formatVarValue` helpers — snake_case key → "Title Case", value formatted
  by unit: `%`-prefixed units multiply by 100, `$`-prefixed units get a `$`
  prefix + comma-separated thousands, everything else is `value unit`).
  `title`/`intro`/`guiding_nudge`/`framework_soundbite`/
  `business_interpretation`/`industry` stay `null` — genuinely not needed for
  swim's screen.
- `waddle`: no AI call, and no facts/question/context narrative at all (pure
  calculation-speed drill). Response adds `formula` (the archetype's raw
  `formula` string) and `variables` (every randomized variable as
  `{ value, unit }`, unit from `template.variables[key].unit`) — deliberately
  NOT a pre-rendered arithmetic expression string (e.g. `"75 × 0.75 × 15"`),
  since building that would require parsing `formula`/`solution_logic` to
  infer operator order, which is fragile. The frontend gets the structured
  parts and formats them however the (not-yet-built) Waddle screen needs.
  `title`/`intro`/`facts`/`question`/`guiding_nudge`/`framework_soundbite`/
  `business_interpretation`/`industry` all stay `null`.
- Both waddle and swim add `display_context` to the response (from
  `templates.display_context`, plain read passthrough) — **only present for
  waddle/swim**; `dive`/`fly` responses don't have `display_context`,
  `formula`, or `variables` — the exact old response shape is preserved for
  existing callers.
- `dive`/`fly`: unchanged — full prose generation exactly as before.

**Flow** (dive/fly; waddle/swim skip step 3 and null the fields it would
have populated):
1. Resolve template: by `template_id` if given, else progressive-relaxation
   filter (`skill_target` → `archetype` → `industry`, dropping filters in
   that order if no matches) using `pickWeightedArchetype` (see
   `_shared/archetype-weights.ts` below) for weighted random selection among
   matches.
2. Call `calculate-case` internally via HTTP fetch (passing through the
   `Authorization` header) for the deterministic math.
3. Call Anthropic (`claude-sonnet-4-5`) with `MASTER_PROMPT` + the resolved
   tone guidance (see "Tone system" below) to wrap the math in a business
   narrative.
4. Insert into `generated_cases`, `status: "approved"`.

**Guardrails baked into the prompt**: unit fidelity (never invent or shift a
time-basis/unit), never invent numbers, **never name a real consulting
firm**, question must match the answer label exactly, never state the
answer, facts must be self-sufficient. A runtime consistency check logs a
`CALCULATOR MISMATCH` error if the AI's narrative conflicts with the
pre-computed math (doesn't block the response, just logs). None of this
applies to waddle/swim since they skip prompt/model entirely.

**Response**: full case row (as inserted) + `relaxed_filters` (which filters got dropped, if any); waddle/swim also add `display_context`.

### `calculate-case`
**Purpose**: deterministic math engine. **Backend-only — never called from
the client**, only from `generate-case` and `get-recommendation` (indirectly,
via `generate-case`).

**Body**: `{ template_id, firm, difficulty }`.

**Reads**: `templates` by id. Writes nothing.

**Flow**: samples `template.variables` (each `{min,max,step,unit}`) scaled by
`DIFFICULTY_PROFILE[difficulty]` (`duckling: {lo:0, hi:0.45, clean:1.0}`,
`billable_bird: {lo:0.25, hi:0.75, clean:0.5}`, `fully_quacked: {lo:0.5,
hi:1.0, clean:0.0}` — `clean` controls how aggressively sampled values get
rounded to "nice" numbers), runs the archetype-specific formula
(`computeArchetype`, one of 15 — see "Archetype coverage"), retries up to
`MAX_TRIES = 80` times against archetype-specific `isSane()` guardrails
(e.g. margins must stay positive, price increases must exceed cost inflation
by ≥3pp) to avoid degenerate cases. `fully_quacked` frequently swaps in a
harder secondary calculation (e.g. after-tax payback instead of pre-tax).

**Response**: `{ template_id, archetype, firm, difficulty, variables, final_answer, worked_solution }`, or **422** if no sane case found after `MAX_TRIES`.

### `get-case-history`
**Body**: `{ user_id, saved_only?, limit? }` (default 100).

**Reads**: `user_attempts` (ordered `created_at desc`), then a second lookup
on `generated_cases` for referenced case ids (FK-independent join, stitched
client-side in the function — `case_id` may point to a deleted row, in which
case `case: null`).

**Response**: `{ history: [{attempt_id, case_id, correct, skipped, response_time, hint_used, saved, attempted_at, case}], count }`.

**Fixed 2026-07-28**: previously selected a nonexistent `generated_cases.firm`
column instead of `tone` — was 500ing on every call. Now correct.

### `get-recommendation`
**Body**: `{ user_id, firm?, difficulty? }` (defaults: McKinsey/duckling).

**Reads**: `user_skills` ordered ascending (weakest first).

**Flow**: no skills yet → `{ mode: "new_user", skill_choices: [...] }` (flattened `templates.skills_tested` across the whole library). Skills exist → internally calls `generate-case` via HTTP fetch with `skill_target` = weakest skill.

**Response**: `{ mode: "recommendation", weakest_skill, score, drill }` (or `drill: null` + note if generation failed for that skill).

### `get-arithmetic-stats`
**Body**: `{ user_id }`.

**Reads**: all of `arithmetic_attempts(operation, correct)` for the user (no pagination — fine at current volume, revisit if this ever gets slow).

**Response**: `{ user_id, total_problems, total_correct, overall_accuracy_pct, by_operation: [{operation, attempted, correct, accuracy_pct}] }` across a fixed 7-operation list. `accuracy_pct: null` = never practiced that operation. Available to all tiers (no gating) — this is a free top-of-funnel hook per `AGENTS.md`.

## `_shared/` helpers

### `service-key.ts`
Resolves the admin/RLS-bypassing key for `createClient()`. Prefers the new
`SUPABASE_SECRET_KEYS` env var (a Supabase-managed JSON secret — actual live
shape confirmed 2026-07-28 to be an object keyed by key name, e.g.
`{ default: {...}, secret_service: {...} }`) over the legacy
`SUPABASE_SERVICE_ROLE_KEY` plain-string var (now fully retired — the legacy
JWT-based keys were disabled in the Supabase dashboard as of this migration).
Parses defensively (array of records / single record / named-object map /
bare string) and prefers a record named `secret_service` if present, then
falls back to matching `secret_jwt_template.role === "service_role"`, then
any usable key. Throws a descriptive error (never logs the secret itself) if
nothing usable is found — there is intentionally **no silent fallback to the
legacy var** anymore, so a broken parse fails loudly instead of masking
itself.

entry ≈20-25%, market sizing ≈15-20% dominate first rounds — directional
industry estimates, not verified firm data). Model: three weight classes
(HIGH ≈52% combined, MEDIUM ≈38%, LOW ≈10%), split ~evenly within each class
across sibling archetypes.

### Tone system

## Known discrepancies / open questions

  — file exists in `supabase/migrations/`, live table doesn't have the column.
- **Dual tier-computation paths**: `AGENTS.md` says `xp` is deprecated for
  tier logic, but `PROJECT_CONTEXT.md` describes a `computeTier` that still
  reads `is_paid`/`xp` in some frontend path, separate from the
  `subscription_tier` column the backend actually gates on. Worth resolving
  which is authoritative and removing the other.
- **Duplicate UPDATE policies** on `user_profiles` (see schema section) —
  harmless, but should be consolidated to one.
- **`generated_cases.status` default (`'pending'`) is never actually used**
  — every insert hardcodes `'approved'`. Fine as-is; just know the default
  isn't meaningful yet unless a moderation step gets added later.
- **`flagged` column (flag-and-redo) referenced in `AGENTS.md` doesn't
  exist** on `user_attempts` — either unimplemented or handled another way;
  don't assume it's there.
- **`archetype-weights.ts`'s "11 not yet built" comment is stale** — only 8
  remain unbuilt (see "Archetype coverage" above).
- **No CREATE TABLE statements are checked into the repo** —
  `supabase/schema.sql` is empty; `supabase/migrations/*.sql` are patch-only.
  This handbook's schema section is the only checked-somewhere ground truth
  until that's fixed (consider running `supabase db dump --schema public` and
  committing the output).
- **`archetypes/*.json` (project root, not `cursor/`) is a design-reference
  artifact, not read by any runtime code.** `calculate-case`/`generate-case`
  read `templates` in the live DB, populated from `supabase/seed_templates.sql`
  — the JSON files are hand-authored source material that predates the seed

  as of Sprint 02 (2026-07-29) the folder still had a single legacy
  `customer_growth.json` and `index.json` said `total_archetypes: 13`, while
  `seed_templates.sql`/production had already split it into 3 archetypes
  (`customer_base_growth`/`ltv_cac_ratio`/`ltv_horizon`) — reconciled this
  sprint by reconstructing the 3 files from `seed_templates.sql`'s data).
  Keep `archetypes/*.json` + `index.json` + `seed_templates.sql` in sync by
  hand; nothing enforces it.
