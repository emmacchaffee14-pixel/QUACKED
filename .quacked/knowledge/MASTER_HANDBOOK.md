# Quacked Master Handbook — Current Standing

**Last synthesized: 2026-08-20.**

This is the top-level entry point into Quacked's knowledge base: what the product actually
does today (the Warm-Up → Waddle → Swim → Dive → Fly → Exhibits progression), what the
backend actually looks like (Supabase schema, Edge Functions, tier gating), and what the
file structure actually is — cross-checked against the live repo, not just against what the
other docs claim. Where a specialized doc has drifted from reality, that's called out here
explicitly rather than silently trusted.

**This doc does not replace the specialized docs below — it sits above them.** It summarizes
and points; the specialized docs remain the deeper source for their own domain.
[`BACKEND_HANDBOOK.md`](./BACKEND_HANDBOOK.md) in particular has a partial auto-sync
mechanism (`<!-- AUTO:...:START/END -->` blocks regenerated by
`cursor/scripts/update-handbook.mjs`) — **never hand-edit its schema/tier-gating tables from
here**; edit this doc's own summaries instead and keep the pointer.

**Kept current by**: a weekly rule (see "Keeping this document current" at the bottom) plus
manual `/update-master-handbook` runs. If you're reading this and something looks wrong,
trust the code and the live DB over any doc — including this one — then fix the doc.

## 2. The learning progression — current build status

Philosophy (from `SWIM_DIVE_METHODOLOGY.md`, still accurate): each environment should own a
distinct cognitive skill, not just different content. **The build status below corrects
several claims in that doc and in `FLY_PHASE_B_SCOPING.md` against what `QA_SYSTEM_ARCHITECTURE.md`'s
2026-08-20 code audit actually found live.**

### Warm-Up — arithmetic fluency
Entry: `Arithmetic.jsx` → `arithmetic-attempt` Edge Function. Live, tier-gated (15/40/unlimited
per day, free/pond/big_duck). **Integrity gap**: the function records attempts but does not
validate `problem`/`correct_answer`/`correct` server-side — the client's own values are
trusted. Flagged as a standing finding in `QA_SYSTEM_ARCHITECTURE.md` §1.4, not yet fixed.

### Waddle — execute the calculation, no recognition step
Entry: `Waddle.jsx` → `WaddleSession.jsx`. `generate-case` with `mode: "waddle"` — zero
Anthropic calls, ~1-2s latency. Curated to a `WADDLE_DIFFICULTY_POOLS` subset (4 archetypes at
beginner, 7 at intermediate, all 15 case-archetypes at advanced) chosen for direct framing and
clean answers — see `BACKEND_HANDBOOK.md`'s `generate-case` section for the full pool
rationale. Live and stable.

### Swim — recognize what to calculate, which formula, what it means
Entry: `Swim.jsx` → `SwimSession.jsx` → `SubModePicker.jsx`. **3 sub-modes exist, but not the
3 `SWIM_DIVE_METHODOLOGY.md` names/describes them as** (per `QA_SYSTEM_ARCHITECTURE.md` §1.2):

| Sub-mode | slug | What's actually built |
|---|---|---|
| Problem Recognition | `problem-recognition` | Matches the doc — archetype-identification MC, no separate LLM call. |
| Formula Finder | `formula-finder` | **3 real exercise types**: a non-scored `FormulaLearnDeck` flashcard pass, an MCQ type (`buildMCOptions`), and a 3-stage `FormulaBuilderCard`/`isBuildCorrect()` build type. The doc's claimed third type — "matching metrics to formulas" — **does not exist in code**. |
| Business Interpretation | `business-interpretation` | Matches the doc's tiering: MC at beginner/intermediate, self-assessed free response (no AI grading) at advanced. |

### Dive — build structure, reason through ambiguity
Entry: `Dive.jsx` → `DiveSession.jsx` → `DiveModePicker.jsx`. **3 live sub-modes, not the 2
`SWIM_DIVE_METHODOLOGY.md` documents** (per `QA_SYSTEM_ARCHITECTURE.md` §1.2):

| Sub-mode | slug | What's actually built |
|---|---|---|
| Structure Building | `structure-building` | The flagship, and the most actively developed surface in the repo right now — recent commits ("Structure Builder Phase H", market_sizing as a sequence-relation archetype) are the newest work in the whole codebase. Grading has migrated from a flat legacy `acceptable_structures` field (still present on only 6 archetype files) to a nested `structure_tree` v2 schema (`supabase/migrations/20260101000020_templates_structure_tree.sql`) now covering ~20 distinct archetypes via `seed_structure_tree_phase_h*.sql` files. `grade-structure` is deterministic and server-side, but must branch on which schema a given archetype uses. |
| Market Sizing | `market-sizing` | **Fully interactive graded builder, not "worked solutions are sufficient"** as the methodology doc still says. `MarketSizingCard.jsx` (586 lines) does approach selection, beginner fact-sorting, intermediate/advanced free-form assumption rows, real tolerance-band grading (`checkMarketSizeAnswer` vs. a server-computed `benchmark_range`), a sanity-check heuristic, and self-assessed rationale comparison. |
| Magnitude Master | *(new — not in the methodology doc at all)* | Real, enabled (`DiveModePicker.jsx`, `MagnitudeMasterCard.jsx`): 8 weighted generator families (`magnitudeFamilies.js` client-side + `_shared/magnitude-master.ts` server-side), 3 answer shapes (numeric/MC/ordering), its own grader `checkMagnitudeAnswer`. **Zero anti-repeat logic on family selection.** |

### Fly — integrate everything under realistic conditions
Entry: `/fly` → `Practice.jsx` directly (`App.jsx`). **`Fly.jsx` was deleted** (commit
`91c81de`) — `FLY_PHASE_B_SCOPING.md`'s central premise, that Fly is a 3-line placeholder and
Practice.jsx is a flat one-shot flow, **is no longer true**. `Practice.jsx` is now 2,260 lines
and implements a real 5-stage loop: `intro → hypothesis → calculate → interpretation →
reflection → done`, gated by a per-user toggle
(`user_profiles.fly_hypothesis_reflection_enabled`, default `true`) that silently skips stages
when off or content is missing. This is essentially what `FLY_PHASE_B_SCOPING.md` proposed as
"Phase B1," shipped after that doc was written. `src/lib/flyEngine.js`/`flyEngineCore.js`
remain confirmed orphaned/unused — the one claim in that doc that still holds.

Grading (per `FLY_CALIBRATION_RUBRIC.md`, a standing decision, not a placeholder): MC at
beginner/intermediate with real-mistake distractors, self-assessed free response against a
shown sample answer at advanced. **No AI/LLM grading at any tier, by design.**

### Exhibits — the sixth pillar, outside the original 5-pillar framing
Entry: `ChartsAndGraphs.jsx` → `ChartsAndGraphsSession.jsx`. 9 live chart archetypes
(`cursor/shared/chartArchetypes/registry.ts`): `simple_bar`, `line`, `pie`, `stacked_bar`,
`stacked_bar_100`, `histogram`, `scatter`, `bubble`, `matrix_2x2`. 5 reserved-but-unbuilt IDs
(`marimekko`, `waterfall`, `break_even_line`, `profitability_bridge`, `market_share`) —
deprioritized, see `EXHIBITS_ARCHETYPE_GAP_AUDIT.md` for the full gap analysis and which of
those would be flat registry additions vs. need genuinely new architecture (a table-exhibit
primitive that doesn't exist yet).

Difficulty calibration: `EXHIBITS_DIFFICULTY_RUBRIC.md`'s 5 dimensions (margin, data volume,
inference depth, insight distance, question framing). Its own flagged "sharpest gap" —
`askFor` branch probability not varying by difficulty — **is now fixed**: two commits
(`e049592`, `608ba9f`, "Batch 4.6 Exception branches + calibration retuning") added
`*_CHANCE_BY_DIFFICULTY` tables to all 9 archetypes. **A gap that rubric doesn't mention and
is worse than it assumed**: `stacked_bar` has zero margin-control code at any tier (confirmed
via grep — no match for `MARGIN|margin` in `stackedBar.ts`), tracked as a `qa_class: system`
finding in `QA_SYSTEM_ARCHITECTURE.md` §7, not yet fixed.

## 3. Backend & Supabase — current state

Full detail lives in `BACKEND_HANDBOOK.md`; this is a current-state summary plus one
correction to that doc's own coverage.

**7 tables, all RLS-enabled**: `user_profiles`, `templates`, `generated_cases`, `user_skills`,
`skill_history`, `user_attempts`, `arithmetic_attempts`. Every Edge Function uses the
service-role key and bypasses RLS; `verify_jwt = false` on every function means auth is not
independently checked against a JWT — each function trusts whatever `user_id` is in the
request body. Flagged in `BACKEND_HANDBOOK.md` as a real, unmitigated risk worth a dedicated
security pass, not something to treat as acceptable long-term.

**⚠️ `BACKEND_HANDBOOK.md` documents 9 Edge Functions; the live repo has 12.** Confirmed by
listing `cursor/supabase/functions/`:

- Documented in `BACKEND_HANDBOOK.md`: `check-gate`, `get-skills`, `update-skills`,
  `arithmetic-attempt`, `generate-case`, `calculate-case`, `get-case-history`,
  `get-recommendation`, `get-arithmetic-stats`.
- **Live but undocumented there**: `generate-chart-exercise`, `grade-chart-exercise` (both
  back Exhibits), and `grade-structure` (backs Dive/Structure Building). This tracks exactly
  with §2's finding that Exhibits and Structure Building are the two surfaces that have grown
  most since the handbook's last full pass — the backend doc's Edge Function inventory simply
  predates them. Worth a `/update-handbook`-style prose pass to add these three, distinct from
  the mechanical AUTO-block regeneration (which only covers schema + tier-gating, not the
  function list).

**Tier gating** (current numbers, mirrored from `BACKEND_HANDBOOK.md`'s auto-synced table —

## 8. Keeping this document current

**Weekly rule**: a scheduled agent runs at the end of every week and refreshes this doc's
current-status sections (§2–§7) against the live repo — re-running the same kind of pass done
here: checking recent commits, re-reading the specialized knowledge docs for new staleness,
and re-deriving file/function/archetype counts from the live repo rather than trusting the
previous version of this doc. **It updates the file only — it does not commit.** Review the
diff and commit it yourself, same as any other change.

**Manual refresh**: ask Claude Code to update the master handbook, or run the
`/update-master-handbook` skill directly (`cursor/.claude/skills/update-master-handbook/SKILL.md`).

**What this doc deliberately does not do**: fully duplicate any specialized doc's detail (schema
tables, full rubric dimensions, full audit tables all stay in their own docs), or take over
`BACKEND_HANDBOOK.md`'s mechanical auto-sync (that stays script-driven and narrowly scoped to
schema + tier-gating). This doc's job is the synthesis and the cross-doc reality check, not
being the single copy of everything.
